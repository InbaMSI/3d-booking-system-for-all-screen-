# Architecture decisions

## Modular monolith before services

The target backend is Django REST Framework with PostgreSQL; Redis/Celery and
Razorpay stay behind explicit interfaces and are introduced only where
required. The Phase 2 scope contains no backend implementation.

## API contract as source of truth

`docs/openapi/cinema-v1.yaml` defines versioned `/api/v1` paths and payloads.
The frontend types are generated by `openapi-typescript`. Local development
uses the contract-shaped mock adapter; `NEXT_PUBLIC_API_MODE=http` selects the
HTTP adapter. The mock is not proof of API conformance, authorization, or
transactional seat allocation.

## 2D and 3D are views over one seat selection

Stable inventory IDs and geometry coordinates are shared by both views.
Selection and price calculation are pure domain functions; server reservation
state is a separate API concern. The procedural scene can later be replaced by
an auditorium glTF without changing the booking contract.

## Payment authority remains on the server

The browser can request a payment order and query status but cannot confirm a
booking. A verified backend event and reconciliation issue a ticket. The mock
never transitions a booking to paid or confirmed.

## Local API prototype

The current interactive backend is a deliberately scoped deviation from the
planned Django REST Framework/PostgreSQL production stack. It uses Next.js route
handlers and SQLite for local persistence, seeds five fictional Chennai
cinemas, and keeps payment unconfigured. Its development-only fixed bearer is
for exercising the frontend contract, not production authentication.
